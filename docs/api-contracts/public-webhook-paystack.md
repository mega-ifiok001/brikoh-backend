# POST /api/webhooks/paystack

Route group: webhooks
Auth: none (merchant-verifiable — the `x-paystack-signature` header IS the credential)
Rate-limited: yes (touches payment data — RULES.md security baseline)

Paystack sends webhook events to this URL (configured in the merchant's
Paystack dashboard). The server verifies the HMAC-SHA512 signature over the
RAW request body using the store's OWN secret key (decrypted server-side from
the store's encrypted PaymentCredential — never from client input), then
processes the event exactly once.

## Request

Headers:
- `Content-Type: application/json`
- `x-paystack-signature: string — required, hex HMAC-SHA512 of the raw body, keyed with the store's secret key`

Body (raw JSON, Paystack event payload):

```json
{
  "event": "string — required, e.g. charge.success | charge.failed | transfer.success | transfer.failed",
  "data": {
    "id": "string — required, Paystack's event id (dedup key)",
    "reference": "string — required, the order's payment reference (ord_…) or the payout's withdrawal reference (wd_…)",
    "status": "string? — Paystack's transaction/transfer status, when present",
    "transfer_code": "string? — Paystack's transfer code, present on transfer events",
    "fee": "number? — the transfer fee in kobo, present on transfer.success"
  }
}
```

Notes:
- The signature is computed over the EXACT bytes received (stringified JSON,
  unparsed). The server never re-serializes the body before verifying.
- The dedup key is `(provider, externalEventId)`, where externalEventId is
  `data.id` — enforced by a unique constraint, so a redelivered event can
  never be processed twice.
- For `charge.*` events, `reference` is the order's payment reference,
  generated by the backend at checkout initiation and echoed by Paystack.
  The order is resolved from it; the store is resolved from the order
  (never from the payload).
- For `transfer.*` events, the payout is resolved from `data.transfer_code`
  (falling back to the `wd_…` reference); the store is resolved from the
  payout.
- Only `charge.success`, `charge.failed`, `transfer.success` and
  `transfer.failed` are handled. Any other event type is acknowledged
  with `200` and ignored (Paystack stops redelivering).

## Success response

Status: `200`

```json
{
  "accepted": true
}
```

`200` is also returned (with the same body) when:
- the event was already processed (redelivery — idempotent no-op), or
- the event type is unknown/ignored.

### `charge.success` processing

In ONE transaction:
1. The WebhookEvent row is created (`PENDING`), guarded by the
   `(provider, externalEventId)` unique constraint — a concurrent redelivery
   loses the insert race.
2. The Order is updated `PENDING -> PAID`.
3. Stock is decremented for each line item through the ledger service (SALE
   entries; the atomic conditional UPDATE rejects any oversell). If stock is
   insufficient, the WHOLE transaction rolls back, an error is returned, and
   Paystack redelivers later. Nothing is half-applied.
4. The store wallet is credited with the order total (`ORDER_PAYMENT` ledger
   entry) — the CARD sale's money enters the wallet exactly when the order
   is confirmed paid.
5. The WebhookEvent row is marked `PROCESSED` with `processedAt`.

If the order is already `PAID` (e.g. processed earlier but the event row was
lost), the event is recorded `PROCESSED` and stock is NOT decremented again
(and the wallet is NOT credited twice).

### `charge.failed` processing

The Order is updated `PENDING -> FAILED` (only if still `PENDING`). Stock is
NOT touched. The event is recorded `PROCESSED`.

### `transfer.success` processing

In ONE transaction:
1. The WebhookEvent row is created (`PENDING`), guarded by the dedup key.
2. The Payout is updated `REQUESTED/PROCESSING -> SUCCESS` with
   `processedAt`; the transfer fee (from `data.fee`, kobo) is recorded when
   present.
3. The WebhookEvent row is marked `PROCESSED`.

If the payout is already `SUCCESS`, the event is recorded `PROCESSED` and
nothing changes (idempotent redelivery).

### `transfer.failed` processing

In ONE transaction:
1. The WebhookEvent row is created (`PENDING`).
2. The Payout is updated `REQUESTED/PROCESSING -> FAILED` with
   `processedAt`.
3. The debited amount is credited BACK to the wallet (a
   `WITHDRAWAL_REVERSAL` ledger entry) — the money that never left returns
   to the available balance.
4. The WebhookEvent row is marked `PROCESSED`.

If the payout is already `FAILED`, the event is recorded `PROCESSED` and
nothing changes (no double reversal).

## Error responses

| Status | Condition |
| ------ | --------- |
| `400`  | Malformed JSON or invalid payload shape (missing event / data.id / reference) |
| `401`  | `INVALID_SIGNATURE` — the signature does not match the store's secret key, or is absent |
| `404`  | `ORDER_NOT_FOUND` — no order with that payment reference (charge events) |
| `404`  | `PAYOUT_NOT_FOUND` — no payout with that transfer code / reference (transfer events) |
| `409`  | `PAYMENT_NOT_CONFIGURED` — the order's provider is unknown or its PaymentCredential is missing, so the signature cannot be verified |
| `409`  | `INSUFFICIENT_STOCK` — stock could not cover the order's line items; the whole transaction rolled back (nothing applied) and Paystack will redeliver |
| `429`  | Rate limited |
| `500`  | Unexpected processing failure — Paystack retries with backoff |

Error body shape (uniform across the API):

```json
{
  "error": {
    "code": "string",
    "message": "string"
  }
}
```

# POST /api/webhooks/paystack-subscriptions

Route group: webhooks
Auth: none (platform-verifiable — the `x-paystack-signature` header IS the credential)
Rate-limited: yes

The PLATFORM's recurring-billing webhook (merchant subscriptions). This is a
SEPARATE trust domain from `/api/webhooks/paystack`: the signature is verified
against `PLATFORM_PAYSTACK_SECRET_KEY` (the platform's own Paystack account),
NEVER the merchant's storefront key. A forged merchant-key webhook can never
touch a subscription, and vice-versa. Point the platform Paystack account's
webhook URL at this endpoint.

## Request

Headers:
- `Content-Type: application/json`
- `x-paystack-signature: string — required, hex HMAC-SHA512 of the raw body, keyed with PLATFORM_PAYSTACK_SECRET_KEY`

Body (raw JSON, Paystack event payload):

```json
{
  "event": "string — charge.success | charge.failed | invoice.payment_failed | subscription.create | subscription.disable | subscription.not_renew",
  "data": {
    "id": "string — required, Paystack's event id (dedup key)",
    "reference": "string? — the subscription payment reference (sub_/upg_)",
    "amount": "number? — the charged amount in kobo",
    "plan": { "plan_code": "string? — PLN_…" },
    "subscription": {
      "subscription_code": "string? — SUB_…",
      "email_token": "string?",
      "status": "string?"
    },
    "subscription_code": "string? — alternate location on invoice/subscription events",
    "email_token": "string?"
  }
}
```

Notes:
- The dedup key is `(provider, externalEventId)` = `("paystack", data.id)`,
  shared with the order webhook's `WebhookEvent` table — redeliveries are
  idempotent across BOTH endpoints.
- Only the events above are handled; any other event type is acknowledged
  `200` and ignored.

## Success response

Status: `200`

```json
{
  "accepted": true
}
```

Also `200` for already-processed (redelivery) and unknown event types.

## Processing

### `charge.success`
Resolves the `SubscriptionPayment` by `data.reference`:
- `sub_…` (kind `SUBSCRIPTION`) — first payment: creates/activates the store's
  `Subscription` (`ACTIVE`), stamps the period window, and links
  `Store.subscriptionId`. Marks the payment `PAID`.
- `upg_…` (kind `UPGRADE`) — the **deterministic upgrade switch**, in one
  transaction: tier + caps + `paystackPlanCode` apply immediately; a NEW
  Paystack recurring subscription is created with `start_date =
  currentPeriodEnd` (create-new-then-disable-old); the OLD subscription is
  disabled; the old code/plan are retained as the `legacy*` snapshot until the
  disable is confirmed. Marks the payment `PAID`.
- `rnl_…` / a renewal keyed only by subscription code — rolls the period
  window and bumps `renewalCount` (only when the current period has actually
  ended; a same-cycle duplicate never extends it twice).

**Guard 1 — same-cycle double charge.** After an upgrade swap, the OLD
subscription may still fire one renewal before its disable lands. A renewal
whose `plan_code`/`subscription_code` matches the `legacy*` snapshot is
recorded as an `orphanReason`-tagged payment with **no local effect** (no
period roll, no `renewalCount`, no grace change).

### `charge.failed` / `invoice.payment_failed`
Marks the `SubscriptionPayment` `FAILED`. A failed RENEWAL flips the
subscription to `PAST_DUE` with `pastDueAt` (the 3-day grace clock); a failed
FIRST payment creates nothing.

### `subscription.create`
Captures the `subscription_code` + `email_token` onto the matching
`Subscription` row (required to disable/cancel later).

### `subscription.disable` / `subscription.not_renew`
Marks the matching `Subscription` `CANCELLED` and clears any pending
downgrade.

## Error responses

| Status | Condition |
| ------ | --------- |
| `400`  | `VALIDATION_ERROR` — malformed JSON or payload shape |
| `401`  | `INVALID_SIGNATURE` — signature does not match the platform secret |
| `429`  | Rate limited |
| `500`  | Unexpected processing failure — Paystack retries |

Unknown references and unknown event types are acknowledged (`200`) without
creating state.
